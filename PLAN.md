# hackensack-next: plan

Living document. Read this before starting work; update it when a decision is made or a milestone lands.

## Goal

A node-based authoring tool for **data-driven pictographic graphics**: playful, illustrative pictures whose structure and appearance are driven by data (how many raindrops, where the sun sits, how grey the clouds are), not charts with axes. You author a **spec** once as a graph of components. At runtime the spec is combined with **data** to produce the picture.

The original 2015 vision also had native iOS/Android interpreters for the spec. That part is dropped: a JS runtime (browser, webview, Node) is the distribution target now. The spec format should still stay portable and declarative so other runtimes remain possible.

Not the goal: competing with Vega/Vega-Lite on charts. Their grammar is built around scales, axes and marks. This tool is built around generating structure from data, closer in spirit to Isotype pictograms and node-based procedural tools (Houdini, Blender geometry nodes). Closest relative in the "author once, interpret at runtime with inputs" space is Rive, which is animation/state-machine oriented rather than structure-from-data.

## Who it's for (under consideration, 2026-11-20)

Not decided; a direction to test. Until now Hackensack has had no user but its own tests, and much of its recent work served the Escapement factory it is built with as much as the tool. Two questions came out of asking whether it has value of its own.

**Its competition is "just ask an AI".** Anyone can now ask for an SVG with one raindrop per 5 mm and get working code in seconds. A Hackensack picture only earns its place where that one-off falls short:
- it outlives the prompt: a spec is a structure you open, read as a graph and adjust, and a component (a sun) stays one definition everywhere it's used;
- it's data, not code: a bundle can only draw registry elements with escaped values, so it's safe to embed and safe to accept from someone else;
- it's a good format for an AI to write into: small, declarative and checked, with problems reported per node. "Describe a weather card" → a spec → fix it by hand in the editor. Untested: whether fixing a generated spec in the editor beats asking again.

**Sightcone could be its first real user.** Sightcone (`~/Relica/dev/sightcone`) is a conversational product over Relica that shows entities on a "glass". Its `docs/dev/VIEW_PACKAGE_ARCHITECTURE.md` splits each view into Query, Actions and UI spec, calls the UI spec "genuinely open", and calls composites as data, views authorable without a deploy, "the research-grade part". Today every glass visual is hand-written React registered by name in `packages/frontend/src/views/ChatPanel/ViewNodeRenderer.tsx` (`COMPONENT_REGISTRY`), and several are Hackensack's kind of picture: `weather-card`, `population-line-graph` (a hand-made `<svg>` polyline), `stat-tile`, the floor-plan summary. `docs/dev/CITY_MEDIA_DESIGN.md` asks for visuals "driven entirely by graph data" where one spec also works on sparse data.
- What fits already: pictures as data; definitions with stable ids (so they could one day live in the graph); a bundle that can't run code, so the backend or an agent can send one; `mount()`, which a single new view type (say `picture`, its data `{ bundle, inputs }`) could call. Sightcone's smart SDK turns language into checked models; a checked picture format is the same idea on the display side.
- What's missing: clicks (Sightcone's cards call `onEntityClick`; the player reports nothing back): a `target` param whose value the player reports on click or hover (#54), with interactivity kept to reporting a value and the host sending state back as data; theme colours (Sightcone colours through CSS variables like `--sc-type-*`, but `mix()` needs real hex values), so a theme is data the host fills in, convention or interface still to decide (#55); and data shaped like a lens result. The player's size (about 875 kB, 211 kB gzipped, mostly math.js) is probably fine for Sightcone for now; #48 has measurements of smaller math.js builds.
- Where it shouldn't go: laying out sections, lists and cards. By Sightcone's own rule ("anything that needs an event loop or pixel knowledge is atomic"), a Hackensack picture is one atomic whose drawing happens to be data, not the composite layer.

If this holds, it gives issues a filter: build what the glass needs before what exercises a factory feature. Hackensack can still be where the factory is tested; it would also have a customer.

**The test:** rebuild Sightcone's `population-line-graph` or `weather-card` as a Hackensack component and show it through one `picture` view type. It passes if it matches the hand-written one and the next picture needs no new React code. If clicks turn out to be needed at once, they become Hackensack's next issue.

## Background: what we learned from Hackensack

Reference repo: `~/Dev/Hackensack` (same author, 2015–2017; got running again Nov 2026 at commit `2870a77`). Its git history has two attempts:

1. **Jan–Jul 2015, first prototype; engine last seen at commit `020a754` (4 Jan 2016). This is the one that worked.**
   - Variable environments inherited down the tree: a node's env = parent's env + its own locals. Root `data` is visible everywhere; `svg_each` layers `<id>_d` / `<id>_idx` per item on top.
   - Expressions solved with **math.js** (`sin`, `cos`, `size`, `pi`, …), per node, per param.
   - DOM rendering; root renders all children.
   - Verified Nov 2026: `test_json/spinner.json` renders correctly in this engine. Changing the root data list from 3 to 6 items makes the spinner go from 3 spokes to 6. Run it with `git archive 020a754` plus the Bower deps from `~/Documents/darkstar_bak/Documents/Hackensack/bower_components`, with the webcomponents polyfill removed.
   - Problem: **speed.** Envs were cloned and pushed down eagerly on every change. `svg_each` re-solved and rebuilt its whole subtree per item, then `cloneNode`d it. Expressions were re-parsed on every evaluation, every edit re-rendered from the root, and there was heavy `console.log` in hot paths.

2. **Jan 2016, second attempt (`68b05f1` onward, now HEAD).** Rendering rewritten to build SVG *strings* and evaluate `{…}` expressions afterwards by regex over the rendered string, with partial evaluation (unresolved expressions kept in braces for an outer pass). Then minilisp replaced math.js, and webpack/React replaced plain scripts.
   - Broke scoping: inside `svg_each`, outer variables like `{cy}` come out as the literal text `cy`. Root only renders `children[0]`. minilisp has only `+ - * /` and lookup.
   - The underlying instinct (partially evaluate a template, finish it when data arrives) was sound. Doing it with regex over strings is what made it fragile.

Other lessons:
- About half the 2015 effort went into a hand-built node canvas (d3, then a custom SVG stage). Use a library.
- The old spec embedded data inside the root node (`data` param as a JSON string). There was no real boundary between spec and data, which is the boundary the whole idea depends on.
- Example specs drifted silently as the engine changed. Examples must be tests.

## Design principles

1. **Spec and data are separate.** A spec declares its inputs; data is supplied at render time. Sample data for authoring lives alongside the spec but is not part of it.
2. **Everything is a component.** Every spec file is a component definition with declared inputs. Compound nodes (a sun, a cloud) and top-level pictures (a weather card) use the same mechanism. Rendering a picture with data means instantiating its outermost component with that data as inputs. See *Compound nodes*.
3. **Lexical scoping via linked frames, never copying.** Each scope is a small frame `{vars, parent}`; lookup walks up the chain. An `each` iteration is one tiny frame. Nothing is pushed down, so there is no propagation cost.
4. **Compile once, evaluate many times.** `compile(spec)` parses and compiles every expression once and returns a `render(data)` function. Editing a node recompiles only that node.
5. **The engine is pure.** No DOM, no editor imports. It produces a plain SVG tree that can be serialized to a string or applied to the DOM. It must run in Node for tests.
6. **Examples are tests.** Every example spec has a golden expected output and runs in CI. If the engine changes, examples either still pass or are migrated in the same change.
7. **Errors stay local.** A bad expression marks its node/param with an error and renders the rest; it never blanks the picture.
8. **Measure before optimizing further.** Principles 3 and 4 should make a few hundred elements trivially fast. Dependency tracking (signals) and in-place DOM patching only get built if measurements demand them.

| Path and polygon nodes | A `path` node whose `d` is plain SVG path data with `{expr}` holes that must give numbers; `=` makes the whole `d` one expression. `polygon` and `polyline` take `points`, a list of `[x, y]` pairs from data or a literal point string with holes. A stored icon is not a new mechanism: an icon is a component wrapping path nodes | A path pasted from an icon works unchanged, and only the numbers that vary become expressions, as transforms already do. | Weather card | `weather-card` combines `sun`, `cloud` and `raindrop` instances. `temperature` → sun height, `clamp(remap(temperature, -10, 40, 112, 36), 36, 112)`; `precip` → a grid of `precip / 10` drops; `cloudCover` → sky `mix('#bfe3ff', '#8a8f99', cloudCover / 100)`, cloud colour and size, sun opacity; `wind` → the cloud drifts and the rain slants by `clamp(remap(wind, 0, 60, 0, 30), 0, 30)` (pixels, and degrees of `skewX`) | Wind reuses the cloud and the drops instead of adding a fifth shape, so it shows on a dry day too. `skewX` rather than `rotate`, which tilted the rows into the cloud. | Name and delete dialogs | The editor asks in its own modal dialog (`AppDialog.tsx`, a native `<dialog>` shown with `showModal()`), never the browser's prompt, alert or confirm. | Make unique (#13) | The inspector's "Make unique…" button, under an instance's Definition select, acts on the selected instance only: it copies the instance's definition as Duplicate does (a new id, its sample copied, refs inside it unchanged) under a name asked for in the name dialog, suggested as the next free numbered name (`sun-2`, then `sun-3`; `nextFreeName`), and points that instance at the copy, keeping its input bindings. The button is disabled, with a hint, when the instance is its definition's only use, and absent for an instance with no definition or a missing one and in read-only projects. The view stays on the parent with the instance selected. Other instances move onto the copy with the Definition select | Keeps the operation small: choosing several instances up front is only a nicer way to repoint them, which the Definition select already does, undoably. Recording the repoint keeps the parent's history whole: a repoint outside the history would leave its earlier steps unable to apply (decided 2026-11-19, #13) |
| Collapse to component (#14) | Collapse acts on one node and its whole subtree: the graph stays single-select, and the inspector's "Collapse to component…" button turns the selected node and everything below it into a new definition, with one instance of it in the node's place. Every variable the subtree reads from outside it becomes an input of the new definition with the same name, so no expression is rewritten: the names its params read (by each param's kind, as `compile` reads it, worked out by `paramNames` in the engine's `names.ts`) and the `inherit` inputs of instances in it that aren't bound, less the names bound inside the subtree on the way down, kept only when the scope at the node defines them (which also leaves out math.js functions, constants, units and the helpers). Each input is typed as the containing component's input when it is one, else `any`, with no default; the instance binds it to the same name (`d: "d"`, and `color: "=color"` for a `string` input, whose bindings are literal text). The instance reuses the node's id, so its slot, saved position and selection stay; the definition keeps the subtree's ids, params and positions. The root and an instance are refused (disabled, with the reason); a loose node, not connected to the root, can be collapsed and its instance stays loose (it sees only the component's inputs, so only those become inputs). The new definition's sample holds, for each input that is an input of the containing component, that component's sample value or else its default; loop variables get none, and with no values there is no sample file. The name dialog suggests `<component>-part`, then `-part-2`. Making the definition isn't undoable (a component operation, as New); replacing the nodes is one recorded step on the parent with no field (`collapseToComponent` in `projectHistory.ts`), which also freezes the parent's automatic layout, so undo puts the nodes back in one go and leaves the new component unused | Multi-node selections across sibling or nested subtrees break scope propagation and would need wrappers; a subtree always has one top and nothing left behind below it, since an instance takes no children and a definition has one root. Keeping names means one shared rule for what a param reads (beside `compile.ts`) and no rewriting; collapsing every node of every example leaves every rendering unchanged (decided 2026-11-19, #14) |
| Animation (#15) | SMIL nodes in the tree, not time-driven data: `animate` and `animateTransform` are ordinary element nodes whose params are expressions read from the data (wind sets how fast a rotor turns), so the output stays plain SVG that animates by itself in any browser, and the engine stays one tree walk per data change with no render loop. Shapes (`rect`, `circle`, `ellipse`, `line`, `path`, `polygon`, `polyline`, `text`) take animation nodes as children, and only those; `g`, `svg`, `each` and `grid` take them too. SMIL's own `fill` (freeze, remove) keeps its name on animation nodes. A `dur` of 0, a negative number or infinity is reported, not silently dropped: a picture that should slow down keeps a floor with `clamp`. The preview has a Pause / Play toggle (`pauseAnimations()` / `unpauseAnimations()` on the live svg), shown only when the picture animates, kept through data edits and not remembered across reloads. `animateMotion`, `set` and time-driven data are later | Simple and portable, and it keeps principle 5 and "wires mean nesting"; a `t` re-rendered per frame would need a render loop and measurements first (principle 8) (decided 2026-11-19, #15) |
| Embeddable player (#16) | The engine moved to its own npm workspace package, `packages/engine` (`@hackensack/engine`, exported as source, no build step); the player is a second package, `packages/player`. A page gets a **bundle**, one JSON file `{ format: 'hackensack/bundle/1', root, components, data? }`: `root` is a component name, `components` the root and every definition it reaches through instance refs (followed by id, in a stable order, `editor` sections dropped; refs inside stay ids), `data` optional default data. One pure `bundle()` in the engine makes it, used by `npm run bundle -- <projectDir> <component> [--sample]` (sample as data only with `--sample`) and by the editor's Export for player button (the top of the trail, unsaved edits included, its sample always as data). The page API is `mount(el, bundle, data?)` returning `{ update, destroy, errors }`, plus a `<hackensack-picture>` element (bundle from `src` or an inline JSON script, data from the `data` attribute or an inline script, the attribute winning; drawn in an open shadow root; `data` and `errors` properties). Given data is laid over the default data **one top-level input at a time**, and each `update` starts again from the defaults. The bundle is compiled once; problems never throw: they show as a small note in the picture (text only) while the valid part draws. ## Spec format v4 (v2 in M1; definition ids added in v3, M4, #3; `expose` removed in v4, #51)

Types: `packages/engine/src/spec.ts`. Working examples: `examples/*/components/*.json`. The spinner as it is stored (`examples/spinner/components/spinner.json`):

```json
{
  "format": "hackensack/4",
  "id": "95ef367e",
  "inputs": {
    "l": { "type": "list" },
    "cy": { "type": "number" }
  },
  "root": "n0",
  "nodes": {
    "n0": { "type": "svg", "params": { "width": 400, "height": 400 }, "children": ["n1"] },
    "n1": { "type": "g", "params": { "transform": "translate(200, 200)" }, "children": ["n2"] },
    "n2": { "type": "each", "params": { "list": "l" }, "children": ["n3"] },
    "n3": { "type": "g", "params": { "transform": "translate(sin(i / count(l) * 2 * pi) * 50, cos(i / count(l) * 2 * pi) * 50) rotate(360 - 360 / count(l) * i)" }, "children": ["n4", "n5", "n6"] },
    "n4": { "type": "circle", "params": { "r": 10, "fill": "#ffffff" } },
    "n5": { "type": "rect", "params": { "x": -10, "width": 20, "height": "cy", "fill": "#ffffff" } },
    "n6": { "type": "circle", "params": { "cy": "cy", "r": 10, "fill": "#ffffff" } }
  }
}
```

Sample data lives in the project's `samples/` folder (`examples/spinner/samples/spinner.data.json`): `{ "l": [1, 2, 3], "cy": 25 }`.

Rules (decided 2026-11-17, M1; ids in M4):
- **Every definition has an `id`**, unique within its library, and instances refer to it by that id (see "Definition identity" above). Format `hackensack/2` had no ids and refs by file name; `hackensack/3` allowed `expose` on a node. Both are reported as older formats and nothing upgrades them (#51): rewrite such a file by hand, giving definitions ids and turning each `expose` into a `vars` node above its node.
- **Children are ordered arrays** on the parent. One parent per node, so the graph is a tree (as in Hackensack). Nodes not reachable from `root` are reported.
- **Editor layout lives in an optional `editor` section**, so the engine can ignore it.
- **How a param value is read depends on its kind** (the node registry, `packages/engine/src/nodes.ts`):
  - JSON numbers and booleans are always literal.
  - For number, length, transform and list params, a string is an expression.
  - For color and string params, a string is literal, so `"#ffffff"` just works.
  - A leading `=` makes any string an expression: `"fill": "=color"`.
- **Lengths** are expressions with an optional trailing `%` or `px` unit (`"100%"`, `"d * 4px"`). The unit is split off before evaluating, because math.js reads `50%` as `0.5`.
- **Transforms** are SVG transform syntax whose arguments are expressions: `"translate(sin(a) * 50, 0) rotate(45)"`. Parsed once at compile time. Allowed functions: translate, scale, rotate, skewX, skewY, matrix.
- **`each` names its bindings** (`as`, `index`, defaults `d` / `i`), replacing Hackensack's `<id>_d` / `<id>_idx`. Inner names shadow outer ones. `each` renders no element of its own: its children are repeated in place.
- **`grid` repeats its children over a count**, in rows and columns (decided 2026-11-18, M5, #6). `count` is a number expression such as `rain / 5`; a fraction is rounded down, so only whole icons are drawn, and 0 draws nothing. Cells are filled row by row, `columns` to a row (default 5). Each cell is drawn inside its own `<g transform="translate(col * spacing, row * rowSpacing)">`, so the children need no position of their own. `spacing` defaults to 20 and `rowSpacing` to `spacing`; a negative `rowSpacing` grows the grid upward. Each cell binds its column, row and index, counting from 0, under the names set by the `col`, `row` and `index` params (defaults `col`, `row`, `n`; `n` rather than `i`, so a grid inside an `each` doesn't hide the `each`'s `i`). If one of those names is invalid, or two are the same, the problem is reported and all three defaults are used. A negative or non-numeric count, a count over 10,000 cells, fewer than one column, a missing count or a failing param is reported on the grid, which then draws nothing; the rest of the picture still renders. A partial last icon (3.5 drawing a half icon) is left for later. Adding the node type needed no format bump: `hackensack/3` doesn't list node types, the registry does.
- **Component inputs** (`inputs`) declare `type` (number, string, boolean, list, object, any), optional `default` and optional `inherit: true`. Instance bindings for `string` inputs are literal like other string params; all other bindings are expressions. **A value of the wrong type is rejected** (decided 2026-11-17): it's reported and the input is left unset, the same as a missing input, with no fallback to the default. This applies whether the value came from top-level data, a binding or inheritance.
- **Numbers in output** are rounded to 6 decimals, and `-0` prints as `0`.
- **Expressions use `count(l)` for list length, not `size(l)`.** In current math.js, `size()` returns a one-element list, and functions like `sin` refuse lists. (The 2015 engine's old math.js allowed it.)
- **Expressions are sandboxed.** They can't assign variables, and math.js's `import`, `evaluate`, `parse`, `compile`, `createUnit`, `simplify`, `derivative` and `resolve` are disabled, since specs may be shared. The helpers below are imported before `import` is disabled, so a spec can't redefine them.
- **Expressions have helpers for mapping data to visuals** (decided 2026-11-18, M5, #7):
  - `remap(value, fromMin, fromMax, toMin, toMax)` maps linearly from one range to another: `fromMin` gives `toMin` and `fromMax` gives `toMax`. It extrapolates outside the input range (wrap it in `clamp` for limits), and either range may run backwards. Equal `fromMin` and `fromMax` is an error ("remap() needs fromMin and fromMax to differ"). It isn't called `scale`, which is a transform function.
  - `clamp(value, min, max)` limits a value to `min..max`. `min` equal to `max` is allowed; `min > max` is an error ("clamp() needs min <= max"), not a silent swap.
  - `mix(colorA, colorB, t)` blends two `#rgb` or `#rrggbb` colours (any case) channel by channel and returns lowercase `#rrggbb`, each channel rounded; `t` is clamped to 0..1. Other colour forms (named colours, `rgb()`, `#rrggbbaa`) are errors. In a colour param it needs the `=` prefix: `"fill": "=mix('#ffffff', '#555555', cloud / 100)"`.
  - They take single values: a one-element list (such as `size(l)`'s result) is unwrapped, a longer list is an error, as with `sin`. A wrong argument count, a non-number, NaN or Infinity is reported naming the helper and the argument. Errors stay local, like any failing expression. The `weather-sky` example uses all three.
- **`path` takes SVG path data with holes in braces** (decided 2026-11-18, M5, #8): `"d": "M 0 0 L {w * 2} {h} Z"`. The text around the holes is kept exactly as written, so a path pasted from an icon works unchanged. Each hole is an expression, parsed once at compile time, that must give a number (a one-element list is unwrapped); it is written like any number in the output (at most 6 decimals, no `-0`). Holes are substituted literally, so adjacent holes need a separator (`M{x}{y}` with 10 and 20 gives `M1020`). There is no escape for a literal brace, since path data never contains one, and a closing brace inside a quoted string in a hole doesn't end it. A leading `=` makes the whole `d` one expression giving text, as for string params. Path data outside the holes is not validated: the browser draws up to the first error, and the engine carries no path grammar. An unclosed `{`, a stray `}`, an empty `{}` or a hole that doesn't parse is a compile problem; a hole that fails or gives text, a list, an object or a non-finite number is a render problem. Either way it is reported on the node's `d`, which is left out, and the rest of the picture still renders.
- **`polygon` and `polyline` take `points`** (#8): an expression giving a list of `[x, y]` pairs, from the data (`"points": "pts"`) or computed. Expressions have no lambdas (assignment is disabled), so computed points use element-wise list arithmetic and `transpose`: `transpose([range(0, count(l) - 1) * 20, 100 - l * 10])` (`range` includes both ends). Or a literal point string, `"0,0 10,0 5,8"`, with holes as in `d`: `"0,0 {w},0 {w / 2},{h}"`. A string is literal when, without its holes, it holds only digits, `+`, `-`, `.`, `e`, `E`, commas and spaces, every token starts like a number, and there is a digit or a hole; anything else (`pts`, `e`, `[[0, 0], [1, 1]]`) is an expression, and a leading `=` always makes it one. Both are written as `x,y x,y` pairs in the usual number format. A one-point list stays a point; an empty list draws nothing and is not a problem (though `transpose` refuses an empty list, so points computed from empty data are reported). A polygon or polyline draws at most 10,000 points. Entries that aren't two finite numbers (named, as in `points[2]`), a result that isn't a list, and an odd number of coordinates or a non-number (`10-5`) in a literal are reported on `points`.
- **`path`, `polygon` and `polyline` also take `fill-rule`, `stroke-linecap` and `stroke-linejoin`** (#8), literal text or `=expression`: `evenodd` for icons with cut-outs, `round` caps and joins for line pictograms. The older shapes don't have them yet.
- **Animation nodes** (#15): `animate` and `animateTransform` draw SMIL elements of those names, with their params as attributes in the order the spec lists them; `animateTransform` always writes `attributeName="transform"` first (it is not a param). They take no children. Their params:
  - `dur` and `begin` are `time` params: seconds, a number or an expression (with or without `=`), written with an `s` (`"60 / wind"` with wind 20 gives `dur="3s"`). `begin` may be negative, which starts the animation part-way through (`-n * 0.2` staggers a grid's cells); `dur` must be more than 0 and finite, else it is reported and left out.
  - `from`, `to`, `by`, `values` and `keyTimes` are `template` params: text kept as written, with `{expression}` holes that must give numbers, as in a path's `d` (`"0 {cx} {cy}"`, `"{r}; {r * 1.12}; {r}"`). A JSON number is written as a number. With `=` the whole value is one expression giving text, a number or a list; a list is joined with `;`, and a list inside it with spaces (`[[0, 0], [10, 5]]` gives `0 0;10 5`).
  - `attributeName` (on `animate`) is an `attribute` param, read like a string: it must be a plain attribute name (letters, digits, `-`, `_`, `:`, `.`), never an event handler (`on…`) or `href`.
  - `type` (translate, scale, rotate, skewX, skewY), `calcMode` (linear, discrete, paced), `additive` (replace, sum) and SMIL's `fill` (freeze, remove) take only their listed values, written or computed (the registry's `options`); anything else is reported and left out. `repeatCount` is text.
  - A missing `attributeName` (on `animate`), a missing `dur`, or none of `to`, `by` and `values`, is reported on the node; the element is still drawn.
  - SMIL's default `additive="replace"` means an `animateTransform` replaces its target's own `transform`: animate a `g` with no transform of its own, or use `additive="sum"`.
  - A shape takes animation nodes directly, and only those: any other child (a shape, `each`, `grid` or an instance) is reported on that child and left out, and the shape still draws. The rule is `childProblem` in `nodes.ts`, used by the compiler, the editor's connect rules and Collapse to component.
  - The preview restarts an animation whenever the data changes, since the markup is replaced. Time-driven data (a `t` variable advanced per frame and re-rendered) is not built; it is a later option.
- **An icon is a component** (#8): a definition whose tree is one or more path nodes, with inputs for what varies (colour, size), reused as an instance like any component. There is no separate icon mechanism. The `pictograms` example shows it: `cloud` is a pasted path coloured by an input, `drop` is a path sized by an input through holes.

### Vars nodes

A `vars` node (#50) names values for its subtree, so a long expression is written once (see *Named values* under Decisions made):

```json
"v1": { "type": "vars", "vars": { "windShift": "clamp(remap(wind, 0, 60, 0, 30), 0, 30)" }, "children": ["n5", "n7"] }
```

- **The names go in its `vars` field**, name to math.js expression, never in `params`: a `vars` node takes no params (any are reported). A `vars` field on any other node type has no effect and is reported.
- **In order.** One frame is filled entry by entry each time the node is drawn (once per item inside an `each`), so a value reads the names before it and anything above the node. A value that reads its own name or a later one in the same node is reported and that name is left unbound: at render time the read would quietly fall through to an outer variable of the same name.
- **Any value** an expression gives: a number, text, a list, a colour. A value must be written as text (`"3"`, not `3`); anything else is reported.
- **Names** must be valid variable names and not math.js constants: `MATH_CONSTANTS` in `expr.ts` (`e`, `E`, `pi`, `PI`, `i`, `phi`, `tau`, `Infinity`, `NaN`, `null`, `true`, `false`, `undefined`, `LN2`, `LN10`, `LOG2E`, `LOG10E`, `SQRT1_2`, `SQRT2`, `version`), refused because a name like `pi` would change what every expression below means (decided at #50's setup). Function names (`max`, `count`, `mix`) are allowed. A name shadows outer names and inputs, as usual.
- **Problems** (a refused name, a value that doesn't compile or fails) are reported on the node with the name as `param`; that name is left unbound and the rest of the picture renders.
- **It draws nothing**: its children's output goes straight into its parent's, with no `<g>`, like `each`. It takes any number of children, but not under a shape (shapes take animation nodes only); a `vars` node above a shape reaches the shape and its animations.
- **One rule, shared.** `compile.ts`'s `readVars` decides which entries bind; `names.ts`'s `varsNames` and `paramNames` (the reads from outside the node), the editor's scope panel (a `vars <id>` frame) and Collapse to component use it, so they can't disagree. In the editor the inspector's *Named values* section adds, renames, edits, reorders (Move up / Move down) and removes names, checked as you type with `edit.ts`'s `varNameError`. The `weather-vars` example is the weather card with its wind shift named once, drawing byte-identical goldens.

## Compound nodes (components)

Node graphs nest. A definition like a sun is authored once, saved to the project's component library, and used as a single node in other compositions, any number of times. This is the same model as Blender node groups, Houdini digital assets and Figma components.

**Project layout (proposal):**
```
my-project/
  components/        # the library: one definition per file
    sun.json
    cloud.json
    weather-card.json
  samples/           # sample inputs for authoring and previews
    weather-card.data.json
```

**Definition** = a spec file (format above): declared `inputs` (its interface) plus a node tree.

**Instance** = a node that references a definition by its `id` (here `sun`'s) and binds its inputs with expressions evaluated in the instance's own scope:
```json
"n7": { "type": "component", "ref": "8c4f9004", "params": { "radius": "d * 2", "rays": "8" } }
```

**Scoping within a graph:** lexical, following the 2015 semantics. A node sees the variables bound by its ancestors on the path to the root (root inputs, `each` bindings, …), nearest first, with inner names shadowing outer ones. It sees nothing from siblings or descendants.

**A node's parameters are not variables (decided 2026-11-17).** Descendants can't read "my parent's `width`". To share a value with a subtree, name it with a `vars` node above it (see *Vars nodes* above) and have the node's param read the name too. Until #51 a node could opt in with `expose`; it was removed in spec format v4.

**Scoping across a component boundary (proposal, agreed in direction 2026-11-17):** components may reach into their surroundings, but **only for names they declare**. Each declared input has a mode:

| Mode | Example | Resolution at each instance |
|---|---|---|
| required | `rays` | Must be bound on the instance |
| default | `radius = 20` | Instance binding, else the default |
| inherited | `palette` | Instance binding, else looked up **by name in the instance's scope** (its chain to the root) |

Like CSS inherited properties (`color` inherits, `width` doesn't). Undeclared caller variables stay invisible inside the definition.

Why the limit: a definition is edited once but used in many surroundings. Without declarations, "what's in scope inside the sun?" has no single answer, the editor can't show a scope panel there, and renaming a variable in one picture could silently break a component used elsewhere. With declarations:
- Inside a definition, the scope panel shows exactly its inputs. Values come from sample inputs, or from the instance the user entered through.
- At each instance, the editor checks that inherited names are provided by the surroundings; if not, it shows a local error badge.
- UX: typing an undeclared name inside a definition that *is* in scope at the entered-from instance offers "inherit `palette` from surroundings?" and adds the declaration.

Instances can sit inside `each` and bind inputs to `d`, `i` and so on.

**Scope panel (editor):** selecting a node lists every variable in scope, grouped by where it comes from (root inputs, `each` n2, inherited inputs, …), nearest first, with shadowed names marked. Hackensack's Env pane (`js/views/env-view.js`, which walks the parent chain) is the precedent.

**Editing semantics:**
- Double-clicking an instance **enters its definition**; a breadcrumb trail (`weather-card › sun`) navigates back out. Edits change the definition, so **every instance updates**.
- The editor shows a **use count** on instances and definitions (Blender's user-count badge), so shared edits are never a surprise.
- Changing a definition's interface (removing or renaming an input) leaves instances with errors on the affected bindings, which stay local (principle 7). It doesn't break the render.
- **Make unique** (#13): copy the definition to a new file (`sun-2.json`) and repoint the selected instance, decoupling it from the shared definition. Blender's "make single user", Figma's "detach". See "Make unique" under Decisions made.
- **Collapse to component** (#14): select a node and turn it and everything below it into a new definition plus one instance in its place; the variables it used from its surroundings become the new definition's inputs, bound at the instance under the same names. See "Collapse to component" under Decisions made.

**Engine:** `compile` resolves `ref`s through a library loader, compiles each definition **once** and caches it, and rejects reference cycles (a sun containing a sun). An instance renders as `definition.render(boundInputs)`, with its output spliced into the caller's tree. This fits compile-once naturally.

## Engine design (built in M1)

Code: `packages/engine/src/` (`@hackensack/engine`). Public API in `index.ts`:

```ts
const program = compile('spinner', library)          // parse and compile every reachable definition once
const { output, errors } = program.render({ l: [1, 2, 3], cy: 25 })
toSvgString(output)                                   // pretty-printed SVG markup
```

- `compile(rootName, library)` takes definitions by name (a project's `components/*.json`). It resolves `ref`s by definition id (`indexById`), compiles each definition once, and rejects reference cycles (`component cycle: a → b → a`). It never throws for spec problems; they go in `program.errors`.
- `program.render(data)` evaluates only. It returns SVG nodes (`{tag, attrs, children}` or text) plus render-time errors. A render error carries a `path` of instance node ids, so an error inside a nested component can be traced to the instance that triggered it. Errors repeated by an `each` are reported once.
- **Scope:** `Frame` (`scope.ts`) is a linked frame that also implements the Map-like interface math.js accepts as a scope, so expressions read straight from the chain. Frames record their source (component inputs, `each`, `grid`, `vars`) for the editor's scope panel. A component instance starts a new chain with no parent.
- **What a spec reads:** `names.ts` works out, without compiling, the names each param of a node reads (by its kind, as `compile` reads it; an instance's bindings by the types of its definition's inputs) and the names `each`, `grid` and `vars` bind, by `compile`'s rules (a `vars` node's through `readVars` itself). `exprNames` (in `expr.ts`, through a handle on math.js's `parse` taken before the sandbox disables it) lists an expression's symbols. The editor's scope panel and Collapse to component use them.
- **Missing or wrong-type inputs** are reported once where the instance is and left out of the frame, so only expressions that use them fail. The rest of the component still renders.
- **Errors stay local:** a failing expression omits just that attribute; an `each` whose list fails renders nothing; a `grid` with a bad count or a failing param draws nothing; an instance whose `ref` matches no definition id renders nothing. The rest of the picture renders either way.
- **Tests:** `engine.test.ts` covers each rule; `examples.test.ts` renders every example against its golden SVG in `examples/*/expected/`. Update goldens deliberately with `npx vitest run -u` after reviewing the new output.

## Open questions

- **Input types:** how rich? Enough for the editor to generate a data form, or just JSON for now?
- **Component children / slots:** can an instance take child nodes (e.g. a `card-frame` component that wraps whatever is plugged into it)? Proposed: not in M1, but keep the format open to it.
- **Preview while inside a definition:** decided in M4 (#1, then #4): the preview shows the picture you entered from with the entered instance highlighted, or, by choice, the definition on its own. See "Entering a definition" under Decisions made. The engine marks what each instance drew with `render(data, { trackOrigins: true })`.
- **Reference identity:** decided in M4 (#3): definitions have stable ids and refs hold them (spec format v3). See "Definition identity" under Decisions made.
- **Where projects live:** for now the editor saves under one folder, `./projects` by default (git-ignored, #5). The goal is decided (see *Projects as documents* under Decisions made): open and save a project anywhere, as a folder with a project file. Still open: the app shell that gives the editor the file system, Electron, Tauri or the browser's File System Access API (#42), and whether the browser build keeps working beside it. The storage interface is in place (#41): the editor reaches files only through a `ProjectStorage`, so the shell is one more implementation, picked in `src/main.tsx`.
- **Sharing a library across projects:** decided in #21: no shared library; components are appended (copied, id kept) from one project into another. See *Projects as documents* under Decisions made.
- **Named values for a subtree:** decided in #22 (which absorbed #38): a `vars` node (#50), and `expose` removed (#51). See *Named values* under Decisions made.
- **Per-instance overrides:** decided in #13: no. Inputs are the only way in; an instance that needs a change is made unique. See "Make unique" under Decisions made.
- **Who it's for:** open. Sightcone's glass is the candidate first user; see *Who it's for* under Goal, and the test there.
