# CLAUDE.md


This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Read `PLAN.md` first.** It holds the goal, the lessons from the earlier Hackensack prototypes, the design principles, the decisions made so far, the milestones and the open questions. Keep it current: record decisions there as they're made and tick off milestones as they land.

Status: M0–M3 done (scaffold, engine, read-only editor, authoring). M4, compound nodes in the editor, is in progress: entering a definition and breadcrumbs (#1), use counts (#2), renaming, duplicating and deleting components and projects with stable definition ids (#3), and the preview inside a definition, highlighted in context or isolated (#4), are done. Browser tests (Playwright) run in the factory's `verify` alongside Vitest (#27). M5 is closed (pictographic primitives): the `grid` repeat node (#6), the expression helpers `remap`, `clamp` and `mix` (#7), the path, polygon and polyline nodes (#8), and the weather card (#9), built from them in the editor, are done. In the editor, undo and redo (#10) is done, with one history per project, and so are editing expose (#11) in the inspector, in-app dialogs for names and deletes (#12), Make unique (#13), which gives one instance its own copy of its definition, and Collapse to component (#14), which turns a node and everything below it into a new definition with one instance in its place. Animation (#15) is done: `animate` and `animateTransform` SMIL nodes whose params come from data, shapes that take them as children, and a Pause / Play toggle in the preview.

## Commands

The project needs **Node 24** (Vite 8 and Vitest 5 need ≥ 22.12; the machine default is 22.11). `.nvmrc` pins it, so run `nvm use` in the repo first. In a non-interactive shell: `source ~/.nvm/nvm.sh && nvm use`.

```
npm run dev            # editor dev server (Vite); saves projects to ./projects (git-ignored)
HACKENSACK_PROJECTS=/some/dir npm run dev   # save projects somewhere else
npm test               # Vitest, one worker, files run one after another
npx vitest run src/engine/index.test.ts   # a single test file
npx vitest run -t 'declares the spec'      # tests whose name matches
npx playwright install chromium   # once per Playwright version; the factory's `setup` runs the same
npm run test:e2e       # browser tests (Playwright), one worker, no retries
npx playwright test e2e/components.spec.ts   # a single browser test file
npm run typecheck      # tsc -b over all tsconfig projects
npm run lint           # oxlint
npm run format         # Prettier (code only; *.md is excluded on purpose)
npm run build          # typecheck + production build
```

Run these one at a time, never in parallel (see Constraints).

## Layout

- `src/engine/`: the engine. `compile(name, library)` → `program.render(data)` → `toSvgString(output)`; `render(data, { trackOrigins: true })` also tags each element drawn inside an instance with `origin`, the path of instance ids that drew it (never serialized); PLAN.md's *Engine design* and *Spec format v3* sections describe the rules. Definitions carry an `id` and instances' `ref`s hold it, resolved with `indexById` (`spec.ts`), never by file name. Node types live in the registry (`nodes.ts`); the structural ones, `each`, `grid` and `component`, draw no element of their own, though a `grid` wraps each cell in a `<g transform>`. `expr.ts` holds the math.js sandbox and the `remap`, `clamp` and `mix` helpers, which check their own arguments; import new helpers there before `import` is disabled. It also keeps a handle on `parse`, taken before the sandbox disables it, for `exprNames` (an expression's symbols). `names.ts` works out from a spec, without compiling, what each param of a node reads (`paramNames`, by the param's kind as `compileParam` reads it, an instance's bindings by `bindingKind`) and what `each`, `grid` and `expose` bind (`eachNames`, `gridNames`, `exposedNames`, by `compile.ts`'s rules); a new param kind or naming rule in `compile.ts` must be mirrored there. `pathdata.ts` holds the `{expr}` hole scanner behind a path's `d` and the `points` reader for `polygon` and `polyline` (a list of pairs, or a literal point string with holes). `smil.ts` holds the animation param kinds (#15): `time` (seconds, written with `s`; `dur` must be positive), `template` (`{number}` holes, or `=` with a list joined by `;`) and `attribute` (a safe attribute name), plus `withChecks`, which applies a param's registry `options` and `positive`; `names.ts`'s `valueNames` mirrors all three. Which children a node takes lives in `nodes.ts`: `children` is `'none'`, `'many'` or `'animation'` (shapes take animation nodes only), and `takesChildren`, `childProblem` and `exposes` state the rule for the compiler, `names.ts` and the editor; never compare `children` with `'many'`. Pure TypeScript that must run in Node (principle 5). Two guard rails enforce this:
  - `tsconfig.engine.json` type-checks it without the DOM lib or ambient types, so `document`/`window` are compile errors.
  - `.oxlintrc.json` forbids imports of React, React Flow or `editor/` code from it.
- `server/`: the dev-server plugin the editor saves through. `projectStore.ts` does the file I/O (tested with temp folders); `plugin.ts` is a thin HTTP layer (`GET`/`PUT`/`DELETE /__hackensack/projects/<root>/<project>/<kind>/<name>`, `POST .../<project>/rename`, `DELETE .../<project>`; every change needs the `X-Hackensack: 1` header). Deleting a project only removes a folder that holds nothing but component and sample files, checked before anything is removed. `examples/` is read-only through it.
- `src/editor/`: the React + React Flow editor. It may import the engine, never the reverse.
  - `api.ts` loads the workspace from the plugin, falling back to `examples.ts` (bundled examples, read-only) when there's no dev server. `projects.ts` holds the project model and pure operations on it: unsaved files plus a queue of files to delete on save (`removed`, never overlapping `unsaved`; `pendingCount` counts both), new/rename/duplicate/delete component, rename/duplicate project, and `nextFreeName` (a copy's suggested name, `sun-2`). `upgrade.ts` upgrades v2 files to v3 on load and `ids.ts` makes definition ids. `commit.ts`'s `commitProject` saves: every write first, then the deletions.
  - `edit.ts`: pure spec edits (add/connect/disconnect/delete nodes, params, root, inputs, exposed params). `scope.ts`: the static scope analysis behind the inspector's scope panel; it takes the names each frame binds from the engine's `names.ts`, and `scopeFrames` also gives each frame's kind. Keep its frames in step with the engine's rules in `src/engine/render.ts`.
  - `collapse.ts`: Collapse to component (#14), pure: `collapseProblem` (the root, instances and animation nodes are refused; a loose node is allowed), `collapseInputs` (the variables the subtree reads from outside it, found with `paramNames`, instances' unbound `inherit` inputs and `scopeFrames`), `collapseSubtree`, `collapseSample`, `collapseName` (`<component>-part`) and `planCollapse`. `collapse.test.ts` collapses every node of every example and checks every rendering is unchanged.
  - `layout.ts` turns a spec into React Flow nodes/edges: root on the right, children to the left, each child's output plugged into a numbered slot on its parent. `BloqNode.tsx` renders a node card at exactly `nodeHeight()` so layout and rendering agree.
  - `trail.ts`: the breadcrumb trail of entered component definitions (`Breadcrumbs.tsx` draws it). The last crumb is the component being edited; the first is the one compiled and previewed. `diagnostics.ts`'s `problemsAt` rebases render problems onto the entered instance. `settleTrail` falls back to the default component when the open one is deleted.
  - `highlight.ts`: `markEntered` flags what the entered instance chain drew (`data-entered`) and dims the rest (`data-dimmed`), on the topmost element only, for the in-context preview. Inside a definition the preview pane's In context / Isolated choice (remembered in `localStorage`) switches to the definition rendered alone with its own sample, and the Sample data pane follows it.
  - `usage.ts`: where each definition is used, and `namesById`/`definitionName`, which every view uses to show an instance's definition by name (refs are ids).
  - `AppDialog.tsx`: the editor's modal dialog (a native `<dialog>`), asking for a name checked as you type with `nameProblem` (`projects.ts`) or confirming a delete. The editor never uses the browser's own dialogs. `App.tsx` holds the open dialog as plain data (`Ask`) and works out its check and action from the latest state; while one is open, the undo and redo keys do nothing.
  - `history.ts`: the undo history, a pure stack of steps (one target each, a component's spec or sample, by definition id), field-visit merging, the 200-step cap, the status-line text and the key mapping. `projectHistory.ts` records edits on a project (`editComponent`, `editSample`) and undoes or redoes them (`undoProject`, `redoProject`), keeping `unsaved`/`removed` honest; `projects.ts` keeps `Project.history` right through saves, renames and deletes. Every graph and inspector edit goes through `App.tsx`'s `onEdit(update, field?)`, and sample data through `editSample`; a component or project operation must not. `collapseToComponent` (#14) is shaped the same way: the new definition and its sample are added unrecorded, and the replacement of the subtree is one fieldless `editComponent` step that also freezes the parent's automatic layout (removing nodes would otherwise rearrange it). `makeUnique` (#13, in `projectHistory.ts` because it records a step) is both: its copy is a `duplicateComponent` (not recorded), and the repoint of the instance is one `editComponent` step on the parent with no field, made outside `onEdit` (a ref change moves nothing, so it doesn't freeze the layout). `datatext.ts`'s `syncDataText` keeps the Sample data text in step with the data after an undo.
  - `App.tsx` owns the workspace state; every graph/inspector change goes through its `onEdit`, which freezes the auto layout before the first edit. It recompiles when the library changes and re-renders on every valid data edit. `PreviewPane` inserts the engine's SVG markup directly, which is safe because the engine only emits registry elements with escaped values. When the picture holds an animation element (`preview.ts`'s `hasAnimation`), it shows a Pause / Play toggle calling `pauseAnimations()` / `unpauseAnimations()` on the live svg; a layout effect applies it again after every markup replacement, and it isn't remembered.
  - Pure logic lives in `.ts` files with tests in `editor.test.ts` (Node environment, no DOM). The React components are checked in a browser, not by unit tests.
- `examples/<project>/`: example projects in the planned layout (`components/*.json`, `samples/*.data.json`) plus `expected/*.svg` golden outputs checked by `src/engine/examples.test.ts`. `raindrops` shows the `grid` node (one drop per 5 mm of rain); `e2e/grid.spec.ts` copies it into its seeded project. `weather-sky` shows the expression helpers (temperature to sun height, cloud cover to sky colour); `e2e/weather-sky.spec.ts` copies it the same way. `pictograms` shows the path, polyline and polygon nodes, with `cloud` and `drop` icons as components; `e2e/paths.spec.ts` copies it the same way. `weather-card`, M5's acceptance case, uses all of them in one picture driven by four inputs (`temperature`, `precip`, `cloudCover`, `wind`), with `sun`, `cloud` and `raindrop` copied unchanged, ids included, from sun-card, pictograms and raindrops (so copying it into the seeded sun-card project overwrites `sun.json` with an identical file); it has three goldens (sample, sunny, stormy), and `e2e/weather-card.spec.ts` copies it the same way and also re-authors its rain from the palette. `windmill` shows animation (#15): a `rotor` component turned by an `animateTransform` whose `dur` follows `wind`, rain falling from a grid (`dur` from `precip`, `begin` staggered by the cell index) and a sun pulsing with an `animate` that reads the `r` its circle exposes; it has two goldens (sample, calm), and `e2e/animation.spec.ts` copies it the same way. A golden mismatch means output changed: review it, then update with `npx vitest run -u`.
- Tests are `src/**/*.test.ts`, run in the Node environment and type-checked by `tsconfig.test.json` (Node types, no DOM).
- `e2e/`: browser tests (Playwright Test, `@playwright/test` pinned to 1.64.1), type-checked by `tsconfig.e2e.json`. `playwright.config.ts` starts its own dev server on `127.0.0.1`, on a free port the OS picks for each run (`HACKENSACK_E2E_PORT` picks one instead), with `--strictPort` and never reusing a running one, and with `HACKENSACK_PROJECTS` set to a fresh temporary folder, removed when the run exits, so they never touch `projects/`. The config runs in Playwright's main process and again in each worker, so whatever a run chooses (the port, the folder) is chosen once and handed down through `process.env` with `??=`. `fixtures.ts` seeds each test its own copy of `examples/sun-card` (components and samples only, which a project delete requires) and has helpers for the editor's in-app dialogs (`dialogOf`, `answerName`, `answerConfirm`); find the Project and Component menus by role (`projectMenu`, `componentMenu`), not by label. The single project sets `testDir: 'e2e'` and there is no top-level `testDir`, so the config's `rootDir` is the repo root and Playwright's JUnit names files `e2e/<file>.spec.ts`, as contract selectors do: `e2e/<file>.spec.ts::<title>` for a top-level test, `e2e/<file>.spec.ts::<Describe> › <title>` for one inside `test.describe` (as in `harness.spec.ts`). Give tests distinctive titles. With `FACTORY_RESULTS_DIR` set, results also go to `$FACTORY_RESULTS_DIR/playwright.xml`. The browser for a run is installed by the factory's `setup` setting, which runs `npx playwright install chromium` and nothing else (no `npm ci`); a developer runs the same once per Playwright version. `check-port-refused.mjs` shows a server already on the port is refused rather than tested. `undo.spec.ts` drives undo and redo (#10); seeded projects open on `sun`, the first component by name, so it picks `sun-card` first. `expose.spec.ts` drives the inspector's Exposed variables section (#11). `dialogs.spec.ts` drives the name and delete dialogs (#12); the status line is `.status`, since the problems panel is also a `status`. `collapse.spec.ts` drives Collapse to component (#14); it writes a `deck` component (an `each` with a group of two shapes, and a loose group) into the seeded project before opening it. `make-unique.spec.ts` drives Make unique (#13); it rewrites a seeded file before opening the project for states the Palette can't make (an instance with no ref, or a missing one, and a component holding an instance of `sun-card`). `animation.spec.ts` drives animation (#15): the palette and inspector, wiring an animate into a circle, the scope panel, the windmill's live preview, moving the SVG clock (`pauseAnimations`, `setCurrentTime`), the Pause / Play toggle and entering the rotor.
- `tsconfig.json` only references the per-area projects: engine, app (editor, with DOM), test, node (`vite.config.ts`), and e2e (browser tests).

## Constraints

- Run tests serially (no parallel workers), and never run several Node/build processes at once. This machine freezes otherwise.
- `react/preserve-manual-memoization` is off in `.oxlintrc.json` because the React Compiler isn't enabled; turn it back on if `react({ compiler: true })` is ever added.
